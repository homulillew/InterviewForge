## 第一组：你为什么决定做这件事

### Q41｜你怎么判断真正该解决的是研究状态管理，而不是模型不够强？

**决策锚点：** C01、C04；问法模式 D01、D09。要求证明问题定位，而不是复述设计。

**参考回答：**

我会先分清失败发生在哪一层。给模型一篇完整论文，它仍然理解错核心机制，这是阅读和推理能力问题；它能正确解释单篇论文，但换会话后丢掉比较条件、反复查同一个问题，或者把已经撤回的结论继续写进报告，就是状态管理问题。两类问题可能同时存在，需要分别定位。

我的选择是把已经形成的研究认知显式保存，并保留证据和修订关系。它针对的是信息在多步、多角色和跨会话传递中的损失。换更强模型可能同时改善多个环节，但很难仅凭最终报告变好就知道问题被哪一部分解决。

要验证判断，我会比较相同模型下有无研究状态的恢复与修订任务，再比较不同模型在同一状态机制下的表现。如果错误主要发生在一次原文理解中，状态只是忠实保存了错误，我就应该优先改阅读和核验，而不是继续扩大记忆结构。

**面试官改条件：** “单篇理解和会话恢复都没问题，仍然漏掉关键论文呢？”——此时优先检查发现策略与证据覆盖；状态管理不是所有问题的统一答案。

### Q42｜你有哪些真正可行的备选方案，为什么最后选了现在这套？

**决策锚点：** C01、C03、C07；接 Q41；D01、D03。

**参考回答：**

我会比较三种复杂度不同的方案。第一种是单会话长上下文加摘要，投入小，适合短任务；第二种是固定检索、逐篇总结、统一生成报告的流程，容易控制和评测，适合目标稳定的资料整理；第三种是根据研究状态交替检索、深读与综合，适合会随着新证据改变方向的任务。

本项目选择第三种，关键条件是问题开放、结论需要反复修订，还要跨会话和跨 Run 复用。固定流程容易在检索阶段提前锁死材料范围，直到最后才发现缺少决定性证据；纯摘要又难维护结论与证据依赖。

我承担的代价是状态模型、生命周期和验收更复杂，因此没有让每个子 Agent 都自治修改全局认知，而是把自由度集中在研究动作选择上，把共享写入和交付边界收紧。

**改选条件：** 如果任务变成固定格式的周报，来源与比较维度长期稳定，我会先用固定流程。任务不再需要的自主性，不值得持续支付维护成本。

### Q43｜什么结果会让你承认这套架构选重了？

**决策锚点：** C01、C07、C08、C10；接 Q42 的复杂度代价；D11、D14。

**参考回答：**

如果在代表性任务上，简单方案在结论支持度、覆盖和恢复能力上已经满足要求，而复杂方案只增加协调、检查和修复成本，我会承认它对这批任务选重了。

这里不能用自己最擅长的超长任务替全部场景作决定。我会按任务跨度、领域熟悉度和跨论文比较难度分层，观察复杂机制究竟在哪一层带来收益。若收益只集中在少数高难任务，就把它设计成按需启用的路径，而不是默认全量运行。

另一个信号是维护成本超过复用价值：状态字段不断加，但没有改善后续动作或错误定位；Gate 给出大量重复反馈，却很少发现影响结论的问题。这样的组件需要缩减或重新定义职责。

架构选择应该能被任务结果推翻。否则任何表现都能被解释成“还需要更多模块”，系统就失去了收敛方向。

**面试官改条件：** “最复杂方案只在 10% 的任务有用，要不要删？”——10% 是题设。先看这部分任务的价值和失败代价，再决定保留专用路径，不能只按任务数量投票。

### Q44｜假设预算突然减少四成，你先砍什么？

**决策锚点：** C03、C07、C10；接 Q42–Q43；D02、D09。四成是预算压力题设。

**参考回答：**

我先守住会影响最终结论的证据核验，再减少重复探索、低信息增量的论文阅读和纯表达层的反复打磨。不能所有环节统一缩减四成，因为不同环节少一次调用的风险完全不同。

比如主要路线已经清楚，再补一篇结果相近的论文，价值通常低于核查决定推荐结论的关键实验。Reader 并行数也需要结合成本和时限调整：并行主要影响等待，不能直接当作减少 Token 的手段。

如果仍然超预算，我会缩小交付范围：明确优先回答哪个问题、哪些比较留待下一轮。预算改变后，应该调整承诺，而不是保持完整报告的外观却悄悄省掉重要核查。

我的排序依据是这个动作能否改变关键判断、失败后果和单位成本。优先砍重复工作，其次砍低价值范围，最后重新协商交付目标。

**改选条件：** 如果用户要的是低风险资料快览，表达完整度和速度可能更重要；如果报告直接用于技术路线选择，关键比较的核验应获得更高预算。

## 第二组：下一步动作是怎样选出来的

### Q45｜面对当前 State，你怎样决定下一步搜索、深读还是综合？

**决策锚点：** C01、C05；D03、D05。

**参考回答：**

我先看阻塞当前研究目标的是什么。如果不知道有哪些主要路线，优先搜索扩展覆盖；已经有相关论文，但关键机制或实验条件不清楚，优先深读；已有足够局部分析，却还不能回答路线差异，就应该综合。

例如想比较两种检索停止方法，A、B 的论文都已经找到，但 B 的停止条件没看清。此时继续搜索更多论文可能只是扩大未读队列，直接补读 B 的方法部分更有价值。等两篇的机制、设置和限制清楚后，再综合条件差异。

我会用“预期能澄清什么判断、代价多大、是否影响交付”来排序。这是一套决策原则，不需要假装模型能给所有动作算出精确的信息增益。重要的是每个动作要有目标，完成后能回看它是否消除了原来的不确定性。

**面试官改条件：** “Gap 都是旧认知生成的，会不会越查越窄？”——转 Q46，检验有没有保留探索能力。

### Q46｜已有 Gap 都很具体，为什么还要花预算搜索新路线和反例？

**决策锚点：** C01、C06、C07；接 Q45；D03、D05。

**参考回答：**

因为 Gap 只能表示已经意识到的未知，不能覆盖尚未进入视野的问题。如果所有动作都由现有 Gap 驱动，系统会越来越擅长补全已有解释，却可能完全错过一条不同机制的路线。

我会在领域地图尚不稳定、时间窗口发生变化、关键结论过度依赖单一路线时，增加探索和反例搜索。随着主要路线收敛，再把更多预算放到决定性缺口上。

这个比例不应固定成每轮必须一半探索、一半补证。对成熟主题、范围明确的任务，定向补证价值更高；对新主题或最新进展调研，过早收敛的风险更大。重点是定期问一次：有没有什么证据出现后会推翻当前结构，我们是否主动找过它。

**改选条件：** 时间极短且用户范围非常明确时，减少开放探索，同时收紧报告的覆盖承诺；不能在缩小搜索后继续声称全面覆盖领域。

### Q47｜什么时候应该停止继续找证据，而不是把“不确定”无限往后推？

**决策锚点：** C07；接 Q45–Q46；D02、D03。

**参考回答：**

我会区分会改变最终判断的不确定性和只增加细节的不确定性。前者值得继续投入，后者可以作为边界保留，不必为了消除所有未知而无法交付。

例如用户要判断哪条路线值得投入验证，当前证据已经能说明适用场景和主要成本，继续核对一个不影响选择的边缘实验，收益可能很小。但如果两条路线的排序依赖一个尚未确认的预算条件，这就是决定性缺口。

因此停止判断同时看研究目标覆盖、关键结论稳定性和下一步动作的边际价值，再由独立 Completion 检查是否存在实质阻塞。找不到新论文不自动等于充分，发现还有未知也不自动意味着必须继续。

**面试官改条件：** “一个小概率反例足以让结论完全翻转呢？”——应按潜在后果提高检查优先级，不能只按出现概率或平均增益排序。

### Q48｜你每轮都重新规划，会不会方向来回摆动？

**决策锚点：** C01、C03、C04；接 Q45 的动态选择；D04。D04 来自题目讲解材料，来源类型见附录。

**参考回答：**

会，所以动态规划需要稳定的目标和明确的变更理由。Research Contract 相对稳定，变化的是为达成目标选择的动作。新证据如果只补充一个细节，不应该把整个研究路线推倒重来。

我会在一波互补阅读完成并综合之后重新评估，而不是每返回一个片段就重新派发全部任务。对已经启动的任务，先判断新信息是否改变它的相关性；仍然有价值就允许完成，避免计划震荡造成重复调用。

如果出现足以推翻主假设的证据，就应及时改方向，不能因为已经投入很多成本而硬做下去。需要稳定的是目标和决策依据，而不是保护旧计划不受挑战。

如果进一步把规划自动化，我会记录变更原因和受影响任务，观察反复撤销、重复派发是否消耗了预算。这是检验规划质量的信号。

**改选条件：** 新证据造成的错误风险大于继续执行的收益时，中断旧任务；仅是措辞或轻微优先级变化时，等待当前阅读波结束再调整。

## 第三组：架构边界为什么划在这里

### Q49｜状态对象拆到什么粒度才合适，为什么不把所有句子都做成节点？

**决策锚点：** C01、C05、C06；D03、D13。

**参考回答：**

我按独立修订、独立引用和独立决策的需要来划分粒度。一个判断如果可能单独被推翻、单独需要原文支持，或者会影响下一步动作，就值得明确表示。只是同一机制解释中的连接句，没有必要都升级成全局对象。

粒度太粗，修改一个局部条件可能需要重写整篇分析，也难以定位受影响的结论；粒度太细，则会制造大量关系维护和上下文组装成本，还可能切断理解一句话需要的条件。

所以单篇论文内部保留带原文定位的具体判断，跨论文层面再表示真正需要综合的 Finding 和关系。是否增加新对象，要能说明它改善了哪个操作，例如修订、核验或恢复；如果只是让图更丰富，就不是充分理由。

**改选条件：** 若大量问题都需要句级审计，可以细化定位；若主要是简短资料梳理，就保留更粗的分析单元。抽象粒度应由操作需求验证。

### Q50｜你为什么把最终综合权交给一个主研究者，而不是让多个 Agent 辩论投票？

**决策锚点：** C03、C06；D01、D06、D12。

**参考回答：**

我需要一个明确的全局状态责任边界。多个 Reader 可以提供不同论文的理解，也可以对同一个判断提出质疑，但“提出意见”和“修改权威结论”是两种权限。

主研究者的职责是把意见放回统一的研究目标和证据条件里综合。投票会把来源相关性、条件不同和重复证据压成票数；如果几个 Agent 读的是同一批材料，它们达成一致也未必增加独立支持。

集中综合的代价是可能引入单个综合者的偏差，所以我保留独立核验和反例输入。关键结论有争议时，可以增加独立解释，但最终仍需明确哪份状态被接受、依据是什么。

**改选条件：** 如果任务存在多个同样合理的价值偏好，产出多方案与分歧说明可能比强行统一更好。即便如此，也应有明确的交付版本，而不是多个 Agent 各自覆盖结果。

### Q51｜遇到相互矛盾的分析，你为什么不先全部保留，让最后写报告时再解决？

**决策锚点：** C01、C06；接 Q50；D03、D06。

**参考回答：**

原始分析和冲突证据应保留，但影响后续决策的冲突不能一直拖到写报告。否则下一轮搜索会把互相矛盾的判断都当作依据，Wiki 也可能提前吸收其中一个版本。

我会在研究状态中明确冲突的位置与当前处理状态。能够通过条件差异解释的，形成带边界的结论；需要更多证据的，记录具体缺口；尚无法消除的争议，保留为争议，而不是强行合成一个确定答案。

写作阶段负责把接受的判断表达清楚，不应临时承担未经核验的研究裁决。把冲突显式化，也能让后续研究知道该补什么，而不是每个新会话重新发现同一个矛盾。

**改选条件：** 对不会影响当前研究目标的局部争议，可以保留并延后；对会改变路线选择的冲突，要在继续扩大研究前优先处理。

### Q52｜你为什么需要自定义 Harness，直接用现有框架不行吗？

**决策锚点：** 项目名称、C01–C07；D01、D03。问题不预设项目使用或拒绝过某个具体框架。

**参考回答：**

我会把通用执行能力和研究语义分开看。工具调用、任务执行、模型接入等能力可以复用框架；研究对象如何修订、什么算证据支持、通过结果绑定哪个版本，则需要由项目定义。

自定义 Harness 的理由应该是这些研究约束需要稳定地落实，而不是认为现有框架都不够好。即便换执行框架，Research State 和验收规则也应该尽量保持清晰，不跟某个框架的临时消息格式绑定。

我会先验证框架能否表达需要的状态更新、权限和失败恢复语义。如果可以，优先复用；如果为了贴合框架反而把一个完整语义修改拆成难以保证一致性的多步操作，才考虑单独实现这一层。

**改选条件：** 团队接入多种执行环境、维护资源有限时，更倾向复用成熟执行组件；只有研究领域规则保留在自己的边界内。自研范围越小，替换成本越可控。

## 第四组：有限资源应该花在哪里

### Q53｜Gate 放过错误和错误地拒绝好结果，你更不能接受哪一个？

**决策锚点：** C05、C07；D02。

**参考回答：**

要看错误影响哪类判断。关键比较错误可能让用户选错技术路线，代价远高于一次额外复核；局部表达问题被过度阻塞，则会造成大量修复成本，却不一定提高决策质量。

因此我会按主张的重要性和错误后果设定处理方式。决定推荐结论的事实、比较和因果解释需要更严格的证据要求；风格与非关键细节可以给建议，不必都成为阻塞项。

严格也不能只是增加拒绝次数。我要同时观察漏检的重要错误、误拒的正确内容，以及因此增加的修复轮次。某个 Reviewer 如果一律拒绝，召回了很多问题但无法交付，也不是有效的质量控制。

**改选条件：** 用户只是快速浏览主题时，可容忍部分表达不完整；结果将用于高成本决策时，提高关键主张的复核强度，同时保持明确的升级路径。

### Q54｜你如何决定一单位预算给 Reader，还是给 Reviewer？

**决策锚点：** C03、C05、C07、C10；接 Q53；D02、D09。

**参考回答：**

我先判断当前瓶颈是缺证据还是已有证据被处理错了。如果决定性论文根本没读到，多加一个 Reviewer 只能反复指出材料不足；如果原文已经足够，但比较条件反复丢失，增加相同阅读未必有用，更应该核验和修复综合过程。

还要看这次投入是否可能改变关键结论。一个 Reviewer 能发现高影响的比较错误，价值可能大于再读一篇重复论文；如果它只是反复改措辞，预算应转移到覆盖和原文检查。

我会结合失败类型和阶段成本做小规模对照，观察增加这类投入后，错误减少还是只是流程变长。这里的预算分配是随研究阶段变化的，不能固定按 Agent 角色平均分。

**面试官改条件：** “检查者自己看不懂论文呢？”——回到能力匹配：让更合适的模型或人工核查关键位置，而不是无限增加同质量的检查调用。

### Q55｜如果可以选不同成本的模型，你怎样分配，而不是全部用最强模型？

**决策锚点：** C03、C07、C10；接 Q54；D02、D09。模型配置是设计题，不声称已有多模型路由实验。

**参考回答：**

我按任务难度、错误后果和错误能否被便宜地发现来分配。结构提取、简单分类等任务更容易用明确约束检查，可以先尝试较低成本模型；跨论文因果比较、冲突解释和决定性交付判断，需要更强的语义能力。

不能只看单次调用价格。便宜模型如果经常返工、输出过长或者漏掉关键条件，总成本可能更高。我会比较完成一个合格任务的总成本，包括重试、修复和检查，而不是只比每次调用。

路由依据也不能只用模型自报置信度。可以结合输入复杂度、缺失字段、不同证据是否冲突以及独立核验结果，决定是否升级。对于特别关键的判断，直接使用更强能力可能比先失败一轮更划算。

**改选条件：** 如果模型间有效成本差异很小、路由维护反而复杂，先采用统一模型；有稳定分层收益后再引入路由。

### Q56｜什么时候应该让人介入，而不是继续让 Agent 自纠错？

**决策锚点：** C07、C09；接 Q53–Q55；D02、D05。

**参考回答：**

我会在人拥有关键外部信息、问题涉及目标取舍，或者自动修复已经没有新进展时请求介入。比如研究范围到底优先质量还是部署成本，这是用户偏好，系统不能靠多轮推理替用户决定。

另一类是关键证据冲突，继续调用同样模型只是在重复同样解释。此时应该把争议压缩成可审阅的问题：当前有哪几种判断、各自依据是什么、缺少哪个信息，以及人需要决定什么。

人工介入也有成本，不能把所有低置信内容都扔给人。先完成可自动获得的材料整理和可逆修复，减少人重复读全套资料的负担；介入后把决定及适用范围记录下来，让后续研究能够继续。

**改选条件：** 纯粹的解析失败、临时工具故障优先自动处理；涉及范围授权、重要价值取舍或持续无法消除的关键争议，才升级给人。

## 第五组：什么知识和规则值得长期保留

### Q57｜研究结果通过验收，就一定值得写入 Wiki 吗？

**决策锚点：** C07、C08；D03、D13。

**参考回答：**

通过验收说明它满足本次研究的相应要求，但是否进入长期 Wiki，还要看未来复用价值。一个任务特有的临时比较、很快过期的参数或纯粹的过程记录，可能没有必要成为长期知识页面。

我会优先沉淀稳定的技术路线、影响决策的机制差异、代表论文和成立条件。具体数字可以保留来源与设置，避免脱离实验语境变成长期结论。

写入的成本包括整理、检索噪声和后续维护，所以不应把“存得更多”作为目标。页面组织要帮助未来研究者定位和判断；如果新内容只重复旧知识，可以更新原页面，而不是再生成一份几乎相同的材料。

**改选条件：** 高频、长期复用的领域值得更精细维护；一次性研究可以只保留完整 State 和可交付报告，暂缓额外的知识组织成本。

### Q58｜遇到同类错误，你怎么判断该改 Prompt、改知识库，还是做训练？

**决策锚点：** C08、C09；接 Q57 的知识用途；D09、D10。

**参考回答：**

我先定位错误是否来自缺信息、任务边界不清，还是稳定的行为能力不足。原文根本没取到，要改发现和读取；知识已经具备，但任务要求没有表达清楚，可以改提示和输出约束；跨大量任务都出现同一种难以用上下文纠正的决策错误，才考虑更系统的数据与训练方案。

训练之前还要确认是否有足够稳定的数据分布和可评价目标。否则把流程缺陷产生的轨迹拿去训练，可能只是在固化错误。不断变化的论文事实也更适合保留在可更新的外部知识中，而不是每次都写进模型参数。

我会先用成本低、容易撤回的改动验证错误机制，再判断是否值得投入更重的方案。选择训练是因为有明确的能力缺口和可用监督，不是因为它听起来更高级。

**改选条件：** 少量领域事实缺失优先知识补充；稳定高频的决策能力缺陷、且已有高质量监督和收益空间时，再评估训练。

### Q59｜加了一条 Error-Book 规则后结果变好了，你凭什么认为是规则起作用？

**决策锚点：** C09、C10；接 Q58 的修复选择；D11、D14。

**参考回答：**

单次前后对比不足以归因，因为模型采样、搜索结果和其他改动都可能影响结果。我会固定可控条件，在相同任务上比较有无这条规则，并保留重复运行的波动。

还要检查改善是否发生在规则预期作用的环节。例如规则要求比较时保留实验预算，应该减少条件丢失的主张，而不只是让文稿更长。若错误减少了，但每次都增加大段无关说明，也需要评估代价。

随后把验证扩展到同机制、不同表面内容的任务，再加一些不该触发该规则的反例，观察误伤。必要时加入一个不含有效机制的普通提醒作对照，区分具体规则的贡献和“多提醒一句”的效果。

**改选条件：** 只有原案例改善、迁移失败或误伤严重时，不把规则提升为全局要求；缩小适用范围，或者撤回重新归因。

### Q60｜一条规则局部有效但全局有害，你如何决定保留、降级或删除？

**决策锚点：** C09；接 Q59；D02、D10。

**参考回答：**

先看能不能明确识别它的有效条件。比如“跨方法比较应提供可对照的结构”，在综述任务中有价值，但如果被写成“所有报告必须使用固定表格”，就会误伤单机制解释。此时应该把规则改成带条件的要求，而不是简单在保留和删除之间二选一。

如果有效条件难以识别，误伤又影响关键结论，就不适合自动全局启用，可以降成特定任务的参考提示或人工检查项。若收益不能复现，或者被新的基础能力覆盖，则应退役。

规则治理需要记录它解决哪类问题、适用范围和回归结果，避免历史上有用就永久保留。回退也要保留版本，才能解释某次结果为何变化。

**面试官改条件：** “两条各自有效的规则同时使用却冲突？”——先识别优先级与共同适用范围，再验证组合效果；单条通过不能证明组合有效。

## 第六组：从实现抬头看系统与产品

### Q61｜宏观上，你怎么区分 Agent、工作流和 Harness？

**宏观锚点：** 项目定位、C01–C07；D05、D07。

**参考回答：**

我从决策权在哪里区分。工作流明确规定主要步骤和转移条件，适合路径稳定、结果要求清晰的任务；Agent 根据目标和观察选择下一步动作，适合执行中才逐渐发现问题结构的任务。实际系统通常同时包含两者。

Harness 提供执行这些决策所需的边界，包括状态、工具权限、预算、持久化、校验和交付规则。它可以承载自适应动作，也可以承载确定性流程。

在我的项目中，模型根据研究状态决定下一步查什么、读什么、怎样综合；状态修改和验收转换受到约束。自主性集中在需要语义判断的地方，程序负责能够明确检查的约束。

因此我不会用“有没有循环”“用了几个 Agent”给系统贴标签，更关心决策如何获得信息、哪些行为被允许，以及结果能否被检查和恢复。

**继续追问：** “所有路径都事先写好了，还算 Agent 吗？”——名称可以讨论，但应诚实描述决策空间；固定流程本身也可能是正确的产品选择。

### Q62｜长程任务的根本难点是什么，为什么不只是上下文窗口大小？

**宏观锚点：** C01、C04、C06；D06、D07、D13。

**参考回答：**

我认为难点是信息、决策和错误会跨步骤相互影响。前面读错一个条件，后面的搜索方向就可能偏掉；再把这个判断压缩进摘要，会让之后的综合把它当成前提。即使全部历史都放得下，也不保证模型正确识别哪些内容已经过期、哪些只是猜测。

长程任务还存在部分可观察性：系统不知道有没有漏掉决定性论文，也不知道一次新搜索能带来多大价值，所以需要边行动边修订计划。

工程上要解决认知状态的持久化、证据关联、修订传播和恢复；策略上要决定探索、补证、综合和停止；评价上要能发现看似流畅却已经偏离目标的结果。上下文容量只解决其中的信息承载问题。

**继续追问：** “状态完全正确就一定成功吗？”——还不够，缺少有效动作、能力不足或来源覆盖不全，都可能让正确保存的状态停留在低质量阶段。

### Q63｜从用户角度看，你到底是在交付一份报告，还是在帮助做一个决策？

**宏观锚点：** 项目名称、C07、C08；D07、D08。

**参考回答：**

报告是交付形式，核心价值是帮助用户更快建立可信的领域理解，并完成后续判断。例如该优先验证哪条技术路线、哪些结果可比较、当前最值得补的实验是什么。

所以一份报告即使语言流畅、引用很多，如果用户读完仍然不知道路线差异和限制，价值就有限。我会把用户任务写进研究要求，并让验收检查这些可观察的理解与判断，而不只看篇幅和格式。

不同用户需要不同投影。刚进入领域的人需要术语与结构；准备做实验的人需要机制、条件和可复现设置；负责人更关心取舍与风险。底层研究依据可以共享，但交付不应一份模板适配所有人。

**继续追问：** “用户说只要一份综述，怎么知道背后的决策？”——先明确用途和范围；若无法获取更多信息，就声明目标读者与交付假设，不擅自代替用户选择研究方向。

### Q64｜即使你做得更可靠，用户为什么不用通用模型直接调研？

**宏观锚点：** C01、C04、C08、C10；接 Q63；D07、D09。

**参考回答：**

用户不会因为我用了更完整的架构就选择它，必须看到实际差异。我的价值主张应该落在长期研究的连续性、关键结论的可核查性和已有知识的复用上。

如果用户持续跟进一个领域，普通一次性调研常常需要重新解释背景、重新定位论文，再人工核查比较条件。这套系统要证明它能够减少这部分工作，同时让用户更容易发现结论的边界和来源。

对一次性的低风险问题，通用模型可能已经足够，我没有必要强行争取所有场景。更合理的是选择确实需要长期积累、反复比较和证据审阅的用户任务，再与用户现有方法做同条件比较。

**继续追问：** “这只是你的价值假设，怎么验证？”——观察实际完成任务的时间、核查和修改负担、后续复用情况，并结合结果质量；不能仅用用户觉得新鲜或报告更长证明价值。

### Q65｜开放研究没有唯一标准答案，你如何定义“做得好”？

**宏观锚点：** C05–C07；接 Q63；D08、D14。

**参考回答：**

没有唯一答案，不等于没有可评价的约束。事实与引用可以核查，比较条件能否成立可以讨论，核心问题有没有覆盖、重要反例是否被忽略，也可以提供具体依据。

我会将评价拆成相对客观的支持度与覆盖，以及面向用户的理解和决策帮助。对于后者，用具体任务检验，比如读者能否解释两条路线的适用条件，能否定位支持某结论的原文，而不是只问“你觉得文章好吗”。

多份不同组织方式的报告都可能合格。评审重点不应是贴近某一份标准稿，而是满足约定要求并保留必要边界。存在专家分歧时，记录分歧落在哪个判断和条件上，而不是强行压成一个没有解释的分数。

**继续追问：** “评委意见相反呢？”——先核对目标读者、评价维度与证据，再看是事实争议还是偏好差异；后者可以保留多维结果，不必伪造一致性。

### Q66｜你的耗时和 Token 指标，为什么不直接等于用户价值？

**宏观锚点：** C10；接 Q63–Q65；D07、D11。

**参考回答：**

它们是系统成本指标，能够支持效率叙事，但不能单独证明用户获得了更好的结果。系统更快，如果把更多核查和修正工作转移给用户，端到端成本可能反而增加。

我会同时看从提出问题到得到可用判断的总时间，包括用户补充要求、查证、修改和等待。还要看报告是否改变了后续行动，以及这种改变是否有足够依据。对长期使用，知识复用降低多少重复劳动也很重要。

所以简历里的降幅需要放在质量与范围约束下解释；产品化后，还需要增加用户侧的任务完成和返工指标。系统 Token 下降只是价值链的一环。

**继续追问：** “用户使用频率高就证明有价值吗？”——不一定，可能是重复失败导致频繁重试；要结合任务结果和使用目的解释行为数据。

## 第七组：更大的系统、实验与未来方向

### Q67｜组件彼此依赖时，单模块消融还能说明什么？

**宏观锚点：** C07–C10；接第一轮收益归因和 Q59；D11、D14。

**参考回答：**

消融回答的是在指定配置和任务条件下移除某组件会怎样，不一定等于这个组件在所有系统中的独立贡献。尤其是组件存在依赖时，直接删除可能改变整个系统的行为甚至让对照失去可比性。

例如 Wiki 依赖已接受的研究状态。如果为了关闭 Wiki 连同状态和验收一起关掉，就无法把差异归因给 Wiki。应尽量保持基础流程，单独改变复用入口；如果要比较完全不同的架构，那是另一个层面的实验。

我会同时做合理的组件组合和整系统基线，观察交互效应。组合收益不能把各个百分比直接相加；某个组件单独效果小，也可能因为另一个必要条件缺失。

**继续追问：** “那是不是总能用存在交互逃避证明贡献？”——不能，依赖关系和对照配置应在实验前明确，机制假设要能产生可检查的预测，而不是事后为任何结果找解释。

### Q68｜从个人研究工具走向团队使用，第一批必须改变什么？

**宏观锚点：** C02、C04、C08；D08、D09。团队化是扩展场景。

**参考回答：**

第一批是明确用户、Run 和知识的所有权，隔离任务和材料，管理并发执行与资源配额，并让失败能够被定位和恢复。这些比先增加更多研究角色更紧迫。

个人工具可以依赖单人按协议串行提交，团队环境则可能同时发起多个任务、修改共享 Wiki，必须把并发和版本规则落实在服务边界里。共享知识还要区分个人草稿、团队接受的内容和受限来源，不能默认所有历史材料都可互相检索。

我会先保留清晰的单 Run 语义，把调度、权限和资源管理加在外层；共享知识通过明确的发布和更新流程进入，避免把多人协作简化成大家写同一个目录。

**继续追问：** “先上数据库是不是就解决了？”——数据库能提供部分持久化与事务能力，用户隔离、授权和语义冲突仍需单独设计。

### Q69｜开放式研究结果不可预测，你能够承诺怎样的服务质量？

**宏观锚点：** C04、C07、C10；接 Q68；D02、D08。

**参考回答：**

我会区分执行层承诺和研究结果承诺。执行层可以围绕任务状态可见、预算限制、取消、已提交进度恢复和失败说明建立明确约束；研究层则依据任务范围与可获得证据，说明什么条件下算完成、何时需要部分交付或升级。

不能承诺每个开放问题都有确定答案，但可以承诺不把预算耗尽伪装成研究充分，不把尚未解决的关键争议藏进流畅报告，并保留结论对应的依据。

产品可以设置不同深度与时限的模式，但每种模式都需要明确质量和范围含义。较快模式意味着更有限的研究承诺，而不是同样完整的结论加一个更短等待时间。

**继续追问：** “用户坚持十分钟内完整解决呢？”——先评估范围是否可实现，提供十分钟内能完成的具体交付及剩余工作；不能用无法验证的承诺掩盖约束冲突。

### Q70｜如果只有一个月继续迭代，你怎样排优先级？

**宏观锚点：** C01–C10；接 Q64、Q68；D08、D09、D10。一个月是规划题设。

**参考回答：**

我会先确定这次迭代主要服务哪个目标：提高研究可信度、降低已有任务成本，还是支持团队使用。目标不同，优先级会不同，不能把所有改进都同时放进一个月。

以提升可信度为例，我优先建立能暴露关键失败的评估任务和运行记录，再修复发生频繁、影响大且原因明确的问题。若错误集中在比较条件丢失，就改证据与综合过程；若主要是覆盖不足，就改探索；若状态恢复导致返工，再加强恢复边界。

每项改动都要有可观察的成功标准和回退条件。月底交付应包含一个可比较的版本及其已知适用范围，而不是一张完成了很多模块的清单。

**继续追问：** “老板要功能，为什么你先做评测？”——解释评测如何缩短选错方向的成本，并把最小评测与一个具体功能或修复绑定交付，避免无限建设基础设施。

### Q71｜模型持续变强，你做的这些工程会不会很快失去价值？

**宏观锚点：** C01、C05、C07、C08；D07、D10。讨论条件变化，不预测具体产品。

**参考回答：**

一部分会，而且应该允许它失去价值。为了弥补模型弱点而增加的细碎拆分、格式修复和重复评审，如果新模型已经稳定解决，就应减少，不能为了保留架构继续支付成本。

长期价值更多来自明确的研究目标、可靠的数据与评测、可追溯的知识积累，以及接入用户实际工作流的能力。状态版本、来源权限和重要结论的责任边界，也不会只因为模型更强就自然消失。

我会用相同任务和约束重新评估新模型，既看质量，也看需要多少外围机制才能达到目标。模型升级后可以重新寻找更简单的系统配置。

**继续追问：** “最后只剩很薄一层编排，项目还有竞争力吗？”——取决于是否持续提供可验证的任务价值；层数多少不是竞争力，稳定的领域评估、知识资产和用户适配才可能形成积累。

### Q72｜哪些经验能迁移到其他 Agent，哪些只适用于学术调研？

**宏观锚点：** C01–C09 的抽象归纳；D07、D08、D12。

**参考回答：**

可以迁移的是：区分权威状态和临时上下文，让关键判断保留依据，对共享修改明确责任，按风险配置验证，并让反馈改变后续行为。这些原则也适用于代码分析、复杂资料处理和多步骤业务任务。

学术调研特有的部分是论文身份、方法与实验的比较语义、文献支持与质疑关系，以及“领域开放问题”和“本次调查缺口”的划分。这些对象不能原样套到所有业务里。

迁移时我会先问新任务的权威事实是什么、有哪些不可逆动作、什么算成功以及错误成本多大。比如有真实交易副作用的任务，需要更强的授权和执行一致性；纯资料分析则更关注证据覆盖和表达忠实度。

所以我迁移的是分析和约束方法，再按新领域定义状态、动作与验收。复用框架不能代替重新理解业务。

**收尾追问：** “用一句话总结你的决策方法。”——先明确用户目标和失败代价，再用最小足够的机制约束关键风险，通过可比较结果决定保留、加强还是删除。

## 决策速查：不要把“看情况”当作结论

### 1. 选哪条执行路径

| 已知条件 | 优先选择 | 接受的代价 | 触发重新选择的信号 |
|---|---|---|---|
| 任务短、材料少、无需持续修订 | 简单上下文与摘要 | 细粒度修订能力有限 | 多次出现条件丢失或跨会话返工 |
| 目标和来源稳定，步骤可事先定义 | 固定流程 | 对新证据改变路线的适应性较弱 | 到最后才反复发现决定性材料缺失 |
| 目标开放，证据会改变计划 | 状态驱动的研究循环 | 规划、状态与验证成本 | 简单任务也被完整复杂流程拖慢 |
| 单篇分析可独立，来源等待明显 | 适量并行 Reader | 合并上下文与协调成本 | 限流、重复工作或串行综合成为主瓶颈 |
| 多执行者要修改同一权威状态 | 明确提交协调与事务边界 | 串行等待或事务管理成本 | 单写者协议无法在真实环境保持 |

这些选择不互相排斥：自适应研究可以使用固定的提交流程，简单任务也可以保留必要的来源核查。要明确每种机制解决的问题，避免整套架构只能全开或全关。

### 2. 下一份预算投给谁

| 当前观察 | 优先投入 | 为什么 | 不应直接采取的动作 |
|---|---|---|---|
| 不知道有哪些主要路线 | 覆盖探索 | 先补可能改变领域结构的信息 | 只围绕当前 Gap 反复补证 |
| 决定性论文已找到但条件不清 | 定向原文深读 | 缺的是局部证据 | 无目的扩大论文队列 |
| 局部材料充分但结论关系混乱 | 综合与语义修复 | 缺的是统一判断 | 用更多相似论文稀释问题 |
| 比较结论有高影响错误风险 | 独立核验 | 检查可能改变用户决策的主张 | 平均分配检查资源 |
| 目标优先级无法从任务中确定 | 人工确认 | 缺的是用户选择 | 让模型反复推理用户偏好 |
| 同类修复重复失败 | 重新归因或能力升级 | 原措施没有处理根因 | 继续重复同样的重试 |

### 3. 是否把信息升级为长期资产

| 内容 | 处理方式 | 需要的依据 |
|---|---|---|
| 已接受且可能跨任务复用的机制与条件 | 进入 Wiki 或更新已有页面 | 研究状态与一手来源 |
| 一次任务的临时决策和未解决缺口 | 留在 Run 状态 | 当前目标与后续处理责任 |
| 重复出现且机制明确的错误 | 形成带适用条件的规则 | 复现、根因与独立回归 |
| 单次异常、原因未明 | 先记录和调查 | 不以一次好转推定因果 |
| 过时或误伤明显的规则 | 降级、限定范围或退役 | 新旧版本的可比较结果 |

## 两条高压分支：练习“条件变了，选择也要变”

### 分支 A：预算、质量与自主性的冲突

**面试官：** “用户只给很少预算，你保留所有 Gate，就做不完。保留还是删？”

**候选人：** 我先明确任务最重要的判断及其错误代价，保留影响这个判断的必要核验，削减重复研究与表达修复。如果预算仍然无法支持原范围，就缩小交付范围。Gate 的角色可以按任务配置，但关键证据不能仅因为赶时间就跳过。

**面试官：** “你总在缩范围，产品体验不就很差？”

**候选人：** 范围调整应该在任务入口尽早体现，而不是临近交付才告诉用户做不完。我会提供预算内具体能交付的内容和更深研究需要的条件，同时改进成本预测。体验的目标是承诺可理解、进度可见、结果可用；用完整报告的外观遮住缺口，会把更大成本留给用户。

**面试官：** “那你为何不一开始就固定流程，根本不用 Agent？”

**候选人：** 如果任务在入口就能确定步骤和材料，固定流程确实更合适。保留自适应研究，是为了应对新证据会改变下一步动作的部分。预算约束下也可以缩小动作空间，优先处理决定性问题，而不是让所有步骤完全开放。

**本分支的判断标准：** 能明确调整哪种承诺和机制；不能用“质量速度平衡”代替具体选择，也不能把“自主”理解成不受预算约束。

### 分支 B：复杂架构与可证伪性

**面试官：** “去掉 Wiki，结果一样好，但 Token 多一点，你的 Wiki 是核心创新吗？”

**候选人：** 这说明 Wiki 在这组条件下主要提供效率价值，而不是提升最终能力上限。是否值得保留，要看节省的重复工作能否覆盖构建和维护成本，及其在连续任务上的稳定性。我不会把成本优化包装成新的研究能力。

**面试官：** “换一个更强模型，连 Token 差异都没了呢？”

**候选人：** 那就重新评估 Wiki 在当前配置下的必要性。若还提供明显的来源导航和跨任务积累价值，可以保留较轻的版本；若这些优势也不存在，就应缩减或取消这条路径。

**面试官：** “你这样是不是没有坚持自己的技术路线？”

**候选人：** 我坚持的是可核查的长期研究目标，不是某个组件必须存在。路线应该在约束变化后更新。可以提前说明什么结果会让我改选，这比结果出来后为原架构找理由更能说明决策质量。

**本分支的判断标准：** 能区分目标稳定与实现可替换；不把投入成本当作继续保留组件的理由，也不因为单次无收益就跳过分层验证。

## 宏观回答的落地方式

宏观问题先给一个明确判断，再用本项目解释机制，最后说明迁移边界。不能只列出“规划、记忆、工具、反思”四个名词，也不能只回到文件、类或接口实现。

| 宏观判断 | 回到本项目的具体例子 | 需要补充的边界 |
|---|---|---|
| 长程困难包含决策依据持续变化 | 反例进入后修订 Finding 并改变搜索方向 | 状态正确仍不代表证据覆盖完整 |
| 自主性应按任务不确定性分配 | 模型选研究动作，程序限制状态与验收转换 | 固定任务可以采用更简单的流程 |
| 可靠性必须对应可观察的保证 | 已提交状态恢复、引用定位、认证失效 | 不承诺开放研究必然得到唯一答案 |
| 成本指标只是用户价值的代理 | Wiki 减少重复研究，但仍要计算用户核查时间 | 快速生成错误报告不算效率提升 |
| 工程要随模型能力重新评估 | 删除不再必要的格式修复或过细角色拆分 | 来源、权限、状态责任仍需明确 |
